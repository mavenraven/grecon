# grecon

A workstream management tool for [Claude Code](https://claude.ai/claude-code) agents running in tmux.

Run multiple Claude Code instances across tmux sessions, then manage them all from one place — see what each agent is working on, which ones need input, jump between them, spawn new sessions, and resume past work after a reboot.

```
+- grecon -- Workstreams -----------------------------------------------+
| Name                      Status    Summary                           |
| api-refactor                                                          |
| +- calm-river             * Work    Adding retry logic to deploy step |
| |  +- shell               * Run     Run full test suite              |
| |  +- monitor             * Run     Test suite completion             |
| +- bright-fox             * Idle    Refactored auth middleware        |
| webapp                                                                |
| +- quick-elk              * Input   Waiting for approval to delete... |
| |  +- wakeup in 4m20s     * Sleep   checking CI build                 |
| infra                                                                 |
| +- bold-hawk              * Work    Migrating config to new schema    |
| |  +- shell               * Run     Running database migration        |
+-----------------------------------------------------------------------+
 j/k navigate  Enter switch  x kill  / search  i next input  q quit
```

## Getting started

### 1. Install

```bash
go install github.com/mavenraven/grecon@latest
```

Requires Go 1.21+ and tmux.

### 2. Start the server

```bash
grecon server &
```

On startup the server reconciles desired state from `~/.grecon/grecon.db` — any workstreams in the database that don't have a running tmux session get restored automatically.

### 3. Add tmux keybindings

Add these to your `~/.tmux.conf`:

```bash
# prefix + g → open grecon dashboard
bind g run-shell 'tmux kill-session -t _grecon 2>/dev/null; \
  tmux new-session -d -s _grecon grecon; \
  tmux switch-client -t _grecon'

```

Reload with `tmux source ~/.tmux.conf`.

### 4. Launch some agents

Create a new Claude Code session from anywhere:

```bash
grecon new
```

This opens an interactive form where you set the tmux session name, Claude instance name, working directory, and whether to use a git worktree. On submit, the workstream is written to the database and the tmux session is created.

Or launch headlessly:

```bash
grecon launch --cwd ~/repos/myapp --worktree --attach
```

### 5. Reboot-safe

After a reboot, just start the server. The reconciliation loop detects that the workstreams in the database don't have running tmux sessions and restores them all — creating tmux sessions and resuming Claude conversations. Summaries appear instantly from the database cache.

### 6. Open the dashboard

Press your tmux prefix + `g` (or run `grecon` directly). You'll see all your running Claude Code sessions, their status, and what they're working on. Press `i` to jump straight to whichever agent needs your attention.

## What it shows

Each row in the tree is a live Claude Code process running in tmux:

- **Name** — the Claude instance name (e.g. `ripe-bolt`), grouped under its tmux session
- **Status** — `New`, `Work`, `Idle`, or `Input` (input rows are highlighted — the agent is blocked waiting for you)
- **Summary** — a one-line summary of what the agent is doing, generated by Haiku

Nested under each agent, grecon shows its active child tasks:

| Child type | What it means |
|---|---|
| **shell** | A Bash command running in the background |
| **monitor** | A Monitor tool watching for events |
| **subagent** | A spawned sub-agent (teammate, workflow, etc.) |
| **wakeup** | A `ScheduleWakeup` timer with live countdown |

## Commands

| Command | Description |
|---|---|
| `grecon` | Open the TUI dashboard |
| `grecon new [name]` | Interactive form to create a new workstream |
| `grecon launch` | Create a workstream (background, scriptable) |
| `grecon server` | Start the background server |

### `grecon launch` flags

```
--name       Custom tmux session name
--cwd        Working directory
--command    Custom command (instead of claude)
--tag        Tag the session (repeatable, key:value format)
--worktree   Create a git worktree for isolation
--attach     Attach to the session after creating it
```

## Architecture: Desired State Reconciliation

Grecon follows the same pattern as Kubernetes: the database holds **desired state**, and a reconciliation loop makes reality match.

### Data flow

```
grecon new / grecon launch
       |
       | writes desired state (workstream, tmux name, claude name, worktree)
       v
  ~/.grecon/grecon.db (SQLite)
       |
       | reads desired state
       v
  Reconciliation loop (server)
       |
       | creates tmux sessions, resumes claude sessions
       v
  tmux + Claude Code (reality)
```

**State only flows downward.** `grecon new` and `grecon launch` write to the database. The reconciliation loop reads the database and makes reality match. Nothing observed from the system is ever written back to the database, with one exception: AI summaries are cached in the database as a performance optimization.

### Data model

All desired state lives in SQLite at `~/.grecon/grecon.db`:

```
workstreams
  id            integer primary key
  worktree      text (git worktree path, if any)

tmux_sessions
  id            integer primary key
  workstream_id integer -> workstreams
  tmux_id       text (lookup key, e.g. "ws-api-refactor")
  display_name  text (tmux session name)

claude_sessions
  id            integer primary key
  workstream_id integer -> workstreams
  session_id    text (Claude session UUID, matches JSONL filename)
  display_name  text (the fun name, e.g. "ripe-bolt")
  summary       text (cached Haiku summary)
  active        integer (1 = running or should be running, 0 = user stopped it)
```

A **workstream** groups a tmux session with one or more Claude sessions.

### Per-field ownership

Every field in the database has exactly one writer. Nothing else touches it.

| Field | Written by | When | Notes |
|---|---|---|---|
| `workstreams.worktree` | `grecon new` / `grecon launch` | Creation | Never changed after |
| `tmux_sessions.display_name` | `grecon new` / `grecon launch` | Creation | Never changed after |
| `tmux_sessions.tmux_id` | `grecon new` / `grecon launch` | Creation | Never changed after |
| `claude_sessions.display_name` | `grecon new` / `grecon launch` | Creation | Generated by `GenerateFunName()`. Never changed after |
| `claude_sessions.session_id` | `grecon new` / `grecon launch` | Creation | Never changed after |
| `claude_sessions.active` | TUI (user action) | User stops/reactivates | Loop observes but does not write |
| `claude_sessions.summary` | Background goroutine | After Haiku generates | Performance cache only |

### What writes to the database

1. **`grecon new` / `grecon launch`** — writes all desired state (workstream, tmux_session, claude_session) in a single transaction at creation time. This is the only place names, worktree paths, and session IDs are set.

2. **Summary generator** — a background goroutine calls Haiku and writes the result to `claude_sessions.summary`. This is a cache for fast display on server restart. It is the only field the server writes to.

3. **TUI user actions** — reactivating an inactive session sets `active = 1`.

Nothing else writes to the database. The discovery loop, the reconciliation, the pane watcher — all read-only.

### Reconciliation (server startup only)

On startup, the server reconciles desired state with reality:

1. For each workstream, find claude_sessions where `active = 1`
2. If the tmux session doesn't exist, create it
3. For each active claude_session, resume it with `claude --resume`
4. If there are no active sessions in a workstream, skip it

This only runs once at startup — not in a loop. If a Claude session exits while the server is running, it stays in the TUI as "Off" until the user reactivates it.

### Discovery loop (read-only, every 500ms)

The discovery loop builds the live view for the TUI:

1. Discovers all Claude processes in tmux via `tmux list-panes` + process tree
2. Parses JSONL logs incrementally (only new bytes since last read)
3. Detects status from the terminal pane content (Working, Idle, Input)
4. Reads claude names and summaries from the DB (read-only)
5. Appends inactive sessions from the DB so they appear in the TUI
6. Broadcasts the full session list to connected TUI clients via Unix socket

**The discovery loop never writes to the database.** Everything it computes (tokens, status, model, background tasks) lives in memory only.

### Open questions

- What should happen when a workstream's worktree no longer exists on disk? Delete the workstream? Keep it as inactive? TBD.
- `grecon adopt` — a command that discovers existing Claude sessions in tmux that grecon doesn't manage, lets the user pick one, and brings it into a workstream. Explicit opt-in instead of automatic adoption. Avoids the complexity of auto-adopting every session on the machine.
- When the reconciliation loop discovers a new Claude session the user started manually inside a managed tmux session, it gets added to the DB with no display name (falls back to project name in TUI). Should it get a `GenerateFunName()` name? That's bossy — the user might have set a name via `-n`. Claude Code has no way to rename mid-session. Could inject a shell alias into the tmux session for renaming. Minor issue, leaving alone for now.

### Pruning (periodic)

Every ~10 seconds, the server prunes stale data:

- `claude_sessions` rows whose JSONL file no longer exists on disk are deleted
- Orphaned `workstreams` and `tmux_sessions` with no remaining `claude_sessions` are deleted

### Status detection

Status is determined by reading each Claude Code tmux pane:

| Pane content | Status |
|---|---|
| Spinner character + `...` | **Working** |
| Contains `Esc to cancel` | **Input** |
| No tokens yet | **New** |
| Anything else | **Idle** |

The pane watcher uses tmux control mode (`tmux -C attach-session`) per session for near-instant status updates, with a 500ms debounce hold to prevent flapping.

### Background task detection

grecon parses the JSONL conversation log to find Bash and Monitor tool calls running in the background. It checks the process tree to verify they're still alive. Completed tasks are identified by `<task-notification>` entries in the JSONL.

### AI summaries

Each session gets a one-line summary generated by Haiku. The server extracts recent activity from the JSONL and calls `claude -p --model haiku` to summarize it. Summaries update lazily and are cached in the database so they survive server restarts.
